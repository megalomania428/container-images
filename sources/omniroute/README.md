Upstream is pinned to `v3.8.1` in `vars.sh`; patches are applied in filename order before the container build.

## Claude Code client version

Patch `0009-add-claude-client-version-override.patch` backports upstream `v3.8.51` version identity (commit `c1e30b7676`, issue #12417) into native Claude OAuth: CLI `2.1.280`, captured billing pair `2.1.280.1e2`, advertised SDK `0.112.1`, and advertised runtime `v26.3.0`. Native billing keeps its existing final-body CCH signing but no longer computes a daystamp suffix. This patch retained the upstream pin and `IMAGE_VER=005`.

`CLAUDE_CODE_CLIENT_VERSION=2.1.280` and `CLAUDE_CODE_CLIENT_BUILD_REVISION=1e2` show the captured default pair. Both overrides are read at request time without rebuilding the image; container environment changes require recreating the container. Version-only overrides retain revision `1e2` rather than inferring a matching build, so paired updates are recommended. `CLAUDE_CODE_CLIENT_VERSION=2.1.283` with `CLAUDE_CODE_CLIENT_BUILD_REVISION=a1b` is only a syntax example, not a verified captured pair.

The common version getter still applies to native messages, bootstrap, OAuth provisioning, quota requests, and CC-compatible bridge User-Agent and billing blocks. The revision override and new SDK/runtime advertisements apply only to the native Claude OAuth cloak. Bridge SDK `0.81.0`, runtime `v24.3.0`, algorithmic billing suffix, and CCH behavior remain unchanged; revision overrides do not affect them. Other provider-specific identity profiles are unchanged.

The patch also connects the configured CC bridge `inject_billing_header` operations to the live executor path before body signing; `v3.8.1` otherwise only runs them in the separate signed-request helper. Bridge billing normalization depends on that pipeline being enabled. Other prompt-transform operations are not newly enabled by this backport.

Unset, empty, or unsafe values independently fall back to the captured version or revision. The upstream safe-token validation is retained: surrounding whitespace is trimmed, then 1–32 ASCII letters, digits, dots, underscores, or hyphens are accepted, starting with a letter or digit. This is not semver or minimum-version enforcement: safe downgrades remain possible. `CLAUDE_CODE_VERSION` is an exported pin, not an environment setting.

As in upstream, an explicit billing-transform `version` takes precedence over the environment, including a custom native `systemTransforms` pipeline. Late custom User-Agent or extra headers can override the final wire headers without synchronizing billing, so explicit overrides may produce inconsistent identity. No Claude Code CLI, actual SDK dependency, or actual Node runtime is installed or upgraded.

## Native Claude OAuth compatibility backports
Patch `0009-add-claude-client-version-override.patch` also backports `149b493d1e` (#2621) and `8b074d2c29` (#2943) onto `v3.8.1` after patches 0001–0008. The native Claude system pipeline drops paragraphs containing Pi identity anchors (`@earendil-works/pi-coding-agent`, `/.pi/`, and the Pi documentation heading); the native executor's active-thinking detection avoids adding context management for disabled thinking. In the separate CC-compatible bridge constraints, forced tool choice removes context management together with thinking; this backport does not add that constraints call to the native executor.
Third-party tool names use Claude Code canonical or PascalCase aliases, with a request-local reverse map restoring client names in responses. The native executor also sanitizes malformed tool schemas while retaining boolean subschemas and avoiding the legacy default-stripping helper; this is not a guarantee that default or annotation contents remain unchanged. Anthropic-shape CLIProxyAPI requests receive the same cloak and schema sanitation while retaining their separate reserved MCP rewrite and reverse map.
The cloak is enabled by default. Setting `CLAUDE_DISABLE_TOOL_NAME_CLOAK=true` disables only the generic third-party tool-name cloak on both paths; existing fixed tool remaps, reserved MCP rewrites, schema sanitation, and removal of paragraphs containing Pi anchors remain active. Only the exact value `true` disables it. This switch is intended for debugging and can expose third-party names to Anthropic.
The cloak follows the upstream path guards rather than identifying only Pi: genuine Claude Code traffic in the native guard is also normalized, including matching MCP names. The selected upstream commits do not exempt typed server tools, so a versioned tool such as `web_search_20250305` can have its protocol name changed; no additional server-tool guard is included in this patch. The schema sanitizer is not a complete JSON Schema validator: malformed scalar `properties`, `$defs`, `definitions`, `patternProperties`, `dependentSchemas`, or `unevaluatedItems` placeholders can remain invalid, and recursion can rewrite both placeholder values and schema-like keys inside default/examples or other annotation objects and arrays. A placeholder-valued `const` is dropped entirely, which weakens that schema restriction.
These backports target the third-party classification failure that reports `Third-party apps now draw from extra usage, not plan limits.` Local patch-application and static checks do not establish Anthropic acceptance or prove that usage is charged to the plan's five-hour window. This patch retained the upstream pin and `IMAGE_VER=005`.

## Responses reasoning effort promotion

Patch `0002-fix-github-models-format-and-claude-haiku-beta.patch` also backports the Responses-to-Chat-Completions reasoning promotion released in OmniRoute `v3.8.37` (release commit `555b21d296`, port of `decolua/9router#1817`). It promotes `reasoning.effort` to `reasoning_effort` and removes the raw `reasoning` object from the Chat Completions request. An explicitly supplied legacy `reasoning_effort` takes precedence and is normalized even when a `reasoning` object is present. The Copilot-specific marker is not included. This request transformation applies to all models, not only Claude; interpretation of `reasoning_effort` depends on each provider's existing code.

Patch `0008-add-codex-gpt-5.6-support.patch` is adapted to normalize both new effort values with the existing model-aware helper, preserving its previous Chat-Completions-to-Responses conversion and Codex max/ultra handling. The upstream pin remains `v3.8.1`.

## Claude Haiku thinking preservation

Patch `0002-fix-github-models-format-and-claude-haiku-beta.patch` also backports the Haiku thinking preservation released in OmniRoute `v3.8.2` (release commit `c8a20b1107`, issue `#2454`). The default Haiku branch keeps `thinking` while still removing `output_config` and `context_management`; the existing patch `0009-add-claude-client-version-override.patch` then re-pairs active thinking with `context_management`.

The `v3.8.42` Claude Code client gate is not backported, and no `x-omniroute-thinking` header workaround is added. Live functional verification is left to the requester after rebuilding the image.

## Known limitations and newly exposed effects

The token-budget fitter itself is unchanged, but forwarding Responses effort activates behavior that previously did not run for that effort. The Responses-to-Chat-Completions translator still does not map `max_output_tokens` to the token-limit fields read by the Claude translator. With `low` effort, a resolved model cap of 64000, and an effective caller limit of 64000, the existing fitter now reduces total `max_tokens` to 2048, including a thinking budget of 1024. Before this backport, the same Responses request lost its effort before reaching the fitter and retained a total limit of 64000 under those conditions. This is a newly exposed reduction for the previously unforwarded Responses effort, not a new fitter implementation. Other budgeted effort levels can also trigger the fallback and leave only 1024 tokens of response room; the low-effort example is not exhaustive. The outcome depends on the resolved cap, effective caller limit, effort-to-thinking mapping, and request parameters. Mapping `max_output_tokens` alone would not fix the fallback when the requested limit equals the cap.

Native active-thinking requests can retain an incompatible temperature or forced tool choice, such as `temperature=0.2` or `tool_choice=required` (translated to `any`); this gap is not limited to Haiku or OAuth credentials. For API-key requests without Claude Code client identity, forwarding Responses effort can newly introduce thinking into such a combination outside the native Claude Code cloak. For native Claude Code clients with any credentials, or the OAuth-token path without an API key, the default Haiku branch previously discarded thinking; preserving it now exposes combinations that were masked on those paths. Other native models can also retain incompatible parameters, including when the executor adds default adaptive thinking. These combinations violate the documented active-thinking constraints, although a live HTTP 400 has not been verified here. The patch does not rewrite temperature or add a native forced-tool guard, and the helpers in the separate signed Claude Code bridge do not establish that native requests are normalized. These token-limit and native-constraint effects are intentionally documented rather than fixed in this backport; live Anthropic acceptance remains unverified.
